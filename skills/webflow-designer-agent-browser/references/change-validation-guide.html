Webflow Designer skill

Validate a change without guessing.

Use the reviewed route when one exists. Read the receipt for what the run proved. Stop when the validator says the evidence is not strong enough.

What this validator does

It checks every relevant changed file, selects a reviewed test when it can, and reports the end state that test proved. A pass is stronger than "the click worked," but it is still limited to the selected test and run.

The normal path

1. Route the change. Pi sends the complete relevant changed-file set to validate_change.
2. Follow the route. A trusted route uses the fixed runner. An unknown route may show one bounded candidate for review. An ambiguous route stops.
3. Read the receipt. Report the semantic result, cleanup state, and failure class when there is one.

Route results

ResultMeaningNext step
Trusted and readyEvery relevant path maps to one reviewed runner.Run trusted validation. No model proposal is needed.
PassedThe fixed runner completed its semantic check and teardown.Report the receipt.
Approval requiredOne bounded candidate is available for an unknown route.Review the exact target, actions, oracle, cleanup, and budget before approving one run.
Insufficient evidence or routing ambiguousThe validator cannot select one safe runner. The exact statuses are insufficient_evidence and routing_ambiguous.Report the gap. Do not guess a test.

Candidate approval is specific

A candidate is typed data, not a script. It can use only reviewed operations, reviewed selector keys, a fixed adapter, a typed semantic check, and adapter teardown. The user approves one exact digest. That approval cannot be reused after the run.

Read before approving. A candidate can still be wrong. Check its evidence, target, actions, expected end state, cleanup, and budget. Declining is a valid result.

How to read the receipt

FieldMeaning
status: passedThe selected fixed runner completed.
semanticOracle: passedThe run reached the state it was required to prove.
cleanup: provedThe run proved its declared teardown.
cleanup: not_provedThe process stopped before teardown could be proved. This is not a claim that cleanup failed.
cleanup: failedThe runner explicitly reported a teardown failure.

Runner output stays private. The receipt contains only the small facts needed to understand the result.

Keep the boundary

  • Do not treat ready as passed.
  • Do not ignore an unknown or ambiguous changed path.
  • Do not weaken selectors, assertions, fixtures, worker counts, or verification assets to make a test pass.
  • Do not claim cleanup completed after a failed process unless the receipt says proved.
  • Do not use corpus discovery as routine end-of-work validation. It is maintenance work.
