Evidence-compiled Webflow validation

How evidence-compiled change validation works

The system turns a large, uneven test corpus into reviewed validation contracts, then runs those contracts through fixed tools. Known changes need no model call. Unknown changes can ask for one bounded proposal, but that proposal cannot execute without an exact human approval.

The idea in one picture

The system has two stages. Offline work can inspect a large corpus and wait for review. Runtime work stays small, typed, and deterministic.

The split is the main safety feature. Runtime observations may report drift or failure. They cannot rewrite trusted selectors, operation cards, mappings, or runners. The discovery report records that boundary as notRuntimePromoted: true. Start with the change validation guide for the normal user path.

Why tests are evidence, not truth

A test suite contains useful behavior knowledge, but it also contains stale selectors, shared helpers, fixture assumptions, retries, quarantined cases, and assertions that prove too little. Counting similar tests would create false confidence.

The unsafe shortcut

Group every fragment that performs a click, then call repeated clicks corroboration. This can merge unrelated targets and turn duplicated helper usage into fake independent evidence.

The implemented rule

Group only fragments with the same hashed behavior anchor. A fragment without a target or helper anchor remains unique and cannot corroborate anything else.

semantic_identity in test-corpus-index.py:556-583 creates the anchor. candidate_id adds framework, subsystem, and structural signature. The report keeps the digest, not the original target literal.

fragment_features canonicalizes only bounded literal targets: direct selector literals, a single data-testid CSS locator, a literal role/name pair, and a local alias made from a literal getByTestId. Dynamic selector values are not promoted to selector targets; a helper-call anchor still follows the conservative rule.

That choice prefers a missed grouping over a false grouping. For validation, a false corroboration is more dangerous because it can help an unsafe candidate appear mature.

How offline compilation works

Bound the source

test-corpus-policy.json names the allowed Playwright and Cypress roots, helper sources, locator source, operation seed, adapters, fixed runners, selector keys, risk classes, retries, and timeouts.

Extract structural fragments

structural_fragments and fragment_features isolate one behavior-sized fragment and record its actions, selectors, semantic assertions, context, cleanup, mutation risk, and warning signals.

Group conservatively

build_discovery groups only matching candidate identities. Quarantined, fixture-dependent, destructive, and raw-wait evidence cannot become positive training evidence.

Reserve an independent holdout

A holdout is valid only when its lineage is unique and another eligible lineage exists. Two tests that call the same helper are not independent simply because they live in different files.

Require review before promotion

Discovery creates review material, not executable knowledge. Promotion requires a semantic assertion, independent corroboration, an independent holdout, safe evidence, and human review.

The real read-only discovery run found 4,462 fragments and 3,189 candidates. It reported zero unanchored corroborations.

The hardening oracle stays offline. webflow-hardening-benchmark.py --repo . --format verify uses temporary Git repositories and synthetic fixtures for identity, provenance, tamper resistance, routing, runner failures, lifecycle leases, privacy canaries, and bounded scale. It never opens a browser, reads credentials, contacts Webflow, or promotes evidence. An isolated campaign ran exactly 100 bounded experiments: 12 identity/parser trials followed by 88 provenance, artifact, routing, runner, lifecycle, privacy, performance, and simplification trials. Every retained candidate kept all hard safety metrics at zero and deterministic output. No candidate was auto-promoted; independent review retained only bounded method-scan consolidation, with the safety oracle unchanged.

How runtime validation works

Every non-ignored changed file takes part in routing. The validator refuses to quietly test the part it recognizes while overlooking an unknown product path.

D0: trusted route

If all changed paths match one reviewed mapping, route_trusted_contracts selects the fixed runner and operation IDs. No model proposal is needed.

D1: bounded candidate

If a path is unknown, the validator exposes a small proposal context. At most one data-only contract can be proposed. It still needs an exact digest approval and a one-time host confirmation token issued after interactive approval, and can run only once.

Multiple runner mappings stop as routing_ambiguous. Missing evidence can stop as insufficient_evidence. These are intended outcomes, not degraded passes.

The model, when used, writes data rather than code. The contract can invoke a reviewed operation, assert a typed fact, or compensate with a reviewed operation. It cannot contain JavaScript, shell commands, arbitrary browser instructions, or an unbounded loop.

The contract is a small intermediate language

designer-validation-contract.schema.json defines a closed JSON shape. validate_candidate_contract then applies checks that a schema alone cannot express. Its semantic oracle is the typed check that asks whether the required end state is true.

  "cleanup": ["adapter-teardown"],

The validator checks source binding, evidence references, selected runner, allowed risk, target fixture, fact types, action dependency order, selector allowlist, retry count, oracle, teardown, and exact tracked budget. Candidate approval binds every material field to a digest; the Pi host issues a one-time confirmation token only after the user approves the displayed details.

A receipt says only what the run proved

default_runner keeps a small private output buffer long enough to classify the failure. The raw text is discarded. Public receipts contain normalized facts only.

Runner resultOracleCleanupWhy
SuccesspassedprovedThe fixed scenario completed its assertion and teardown.
Semantic assertion failurefailednot_provedThe end state was wrong, and the failed process did not prove teardown.
Timeout, setup, infrastructure, or unknown failurenot_runnot_provedThe process failed before it could prove the full contract.
Explicit teardown failurenot_runfailedThe runner specifically reported a cleanup failure.

classify_runner_failure owns these distinctions. execute_runner returns passed only after every selected fixed runner succeeds. This avoids the common overclaim that a failed process somehow proved its cleanup.

Browser ownership stays where it already belongs

The validator does not introduce a second browser agent. It selects existing fixed Playwright scenarios and preserves the managed browser and CDP boundaries. test-scenario-eval.py::build_plan can describe setup, browser, assertion, and teardown phases, but it does not execute the adapter.

DesignerCodeMode._validate_change exposes routing, trusted execution, candidate submission, and one-run candidate execution through compact JSON. Existing Webflow scenario utilities still own their own Playwright contexts.

What PICO contributed

PICO is used here as a comparison discipline, not as a clinical-study claim.

Problem / population

Webflow Designer changes whose correctness depends on browser-visible application state and uneven test evidence.

Intervention

Compile evidence offline into reviewed operations and typed contracts, then execute fixed runners with semantic oracles and cleanup proof.

Comparison

Open-ended browser reasoning, raw trajectory replay, action-similarity scoring, LLM-as-judge verdicts, ad hoc test selection, and runtime self-evolution.

Outcomes

Fewer model calls, deterministic routing, bounded execution, semantic end-state evidence, honest cleanup, compact receipts, and no automatic promotion.

What this system does not claim

  • It does not validate every possible Webflow change.
  • A pass proves only the declared oracle and teardown for that run.
  • A hash does not prove that a selector is still fresh.
  • A repeated test pattern does not become truth through frequency.
  • A failed process does not prove cleanup.
  • The runtime is normally model-free, not universally model-free.
  • Paper results explain design choices. They do not prove this implementation correct.

Expand one operation family at a time: review independent evidence and a semantic canary, add one fixed adapter, then rerun the complete affected tests.
