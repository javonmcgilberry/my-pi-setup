Webflow browser / lifecycle guide

A safe Designer run begins before the browser and ends after it.

The lifecycle is a transaction with a declared target, an owned runtime, readiness evidence, a bounded browser handoff, and a cleanup proof. A page load is only one observation; this guide follows the full prepare-to-finish contract, including what happens when a step blocks.

Use it to understand when work may begin, what evidence is enough, and why cleanup is an assertion rather than a courtesy.

Audience: Webflow users and maintainers Default: isolated managed profile Outcome: proceed, block, or recover safely

01 / promise

What one transaction promises

A transaction gives one caller a defined turn with a managed browser. It names the target before launch, proves that the runtime is the one it owns, checks the conditions that make Designer work meaningful, and records enough evidence to make a decision without copying the browser’s private state.

The normal shape is:

  1. Prepare. Validate the declaration, check services, start the managed runtime only when it is unowned, and claim its exclusive lease.
  2. Handoff. Connect the selected transport, perform the explicitly requested Auth Vault login if applicable, open the exact target, and wait for the declared selector.
  3. Verify. Classify URL and title evidence, surface identity, runtime identity, and all five readiness checks.
  4. Act. Choose fast or guarded work only after verify permits it.
  5. Finish. Release ownership, stop only the owned runtime, prove the stopped state, and then retire the automation session.
Important boundary. The browser transport executes the returned plan. It does not get to replace an exact URL, invent a selector, change transports, or decide that a blocker is harmless.

The run closes only when the runtime is proved stopped

Prepare creates a bounded handoff; verify earns work; finish retires ownership.

Finish is not a courtesy after the test. It is the final assertion about who owned the browser and whether that ownership is gone.

Five checks must agree before QA is allowed

Readiness is a conjunction, not the presence of one familiar control.

The five names make a failure actionable. A missing HUD, an expired profile, and a wrong document are different blockers with different fixes.

02 / handoff

Prepare is a gate, not a browser shortcut

Preparation accepts the exact target, surface selector, readiness selector, mode, and transport. The target is preserved as supplied, including meaningful pageId, simulateRole, host, and port values. Credentials and sensitive query parameters are rejected.

If checks is omitted, the lifecycle uses the documented service defaults: https://wfdev.io:8443/ for both hud and designer_service, plus target_http for the exact target. A failed default probe is a named blocker. It is not permission to guess another port or endpoint.

For isolated work, check the sessionless Auth Vault list first. Use authProfile only for an exact, dedicated Webflow profile that the user or private setup identified. A saved Vault name is an authentication attempt, not proof that the requested Designer document is available. If there is no identified profile, stop for the headed authentication gate unless the user authorizes it.

Once service preflight passes, preparation proves that no live runtime owner is present, starts Chrome for Testing, waits for a local direct browser-control endpoint (CDP), claims the exclusive agent_browser lease, and records a private receipt. The returned actions are ordered:

connectauth loginexact openwait

The login action appears only when the exact profile was requested. Preparation never takes a snapshot. The surface remains pending until verify observes it.

03 / signals

Readiness means all five checks pass

The five checks answer different questions. Together they say that the environment, the browser, and the document are all ready enough for the requested work.

hudThe declared HUD service responds.
designer_serviceThe required Designer service responds.
target_httpThe exact target responds without connection refusal or a gateway failure.
browser_profileThe managed Chrome for Testing profile is ready.
designer_surfaceThe approved Designer document is authenticated, not a login document, and not a Chrome error page.

auth_required, unavailable, and error are blockers. A fixed sidebar control is not a readiness check: Designer shells vary by role, and a control can exist while the target document is wrong.

04 / proof

Verify the surface before you inspect it

After the handoff, classify the compact URL and title result before capturing page content. The proof needs the exact URL, a Webflow Designer title on an approved origin, a non-login document, no Chrome error page, and an observed scoped surface. Only then may a snapshot or screenshot support the authorized task.

For an iframe or extension, verify the expected origin and route, then inspect the matching frame. The canvas commonly lives in an iframe while panels and selection UI remain in the parent. Duplicate frames can appear; choose by URL, geometry, and target signal. Do not treat a broad first match as proof.

Evidence should be semantic first: text, counts, roles, data attributes, component IDs, field names, and selection state. Use a screenshot for layout, spacing, color, or transformed canvas content. Filter diagnostics before opening request details, use metadata-only HAR capture by default, and return only a small sanitized object from evaluation.

Privacy rule. Never return cookies, storage values, tokens, credentials, raw DOM dumps, the complete Designer API model, or customer data. Keep screenshots, JSON, HAR files, traces, and profiles outside the repository.
05 / effect

Act only in the lane the effect permits

The fast lane is read-only observation after the complete proof. It can inspect visible text, layout, spacing, color, scoped screenshots, and bounded diagnostics. It cannot navigate, reload, select, edit, publish, or invoke a connected app.

The guarded lane covers every stateful or uncertain action: navigation, reload, selection changes, canvas edits, undo, redo, publish, connected apps, and account, security, or privacy changes. Capture a small baseline, obtain the required authorization, perform one bounded action, and verify the postcondition plus unrelated state.

If the action does not fit the current transaction’s approved scope, finish it cleanly and prepare a new guarded transaction. Do not downgrade the lane to avoid authorization.

06 / closure

Finish is the final proof

Put cleanup in a finally path, including after a failed browser action. Keep the order exact:

  1. Call finish with the transaction ID and same transport, or release the exact standalone lease.
  2. Confirm runtimeOwned: false, cdpReady: false, consumer: null, leasePresent: false, and status: "stopped".
  3. Only after that proof, close the selected native or CLI automation session.

Finish never signs out, clears cookies, or resets the dedicated profile. For an already-finished transaction, the lifecycle still returns the public stopped-runtime fields. That makes cleanup idempotent and keeps “nothing is running” observable rather than inferred.

07 / interruption

Recover by classification, never by guess

After an interruption, call status without changing the runtime. It classifies the transaction, runtime, lease, and whether a recovery action is safe. reconcile is deliberately narrow: it converges only the stale state that the classifier marks safe.

Status classificationMeaningResponse
stale_leaseThe runtime is stopped and a stale lease remains.Reconcile when the classifier says safe; successful reconciliation exits 0.
stale_transaction or stale_transaction_leaseState remains after the runtime has stopped or lost the active lease.Use only the classified finish/reconcile path.
transaction_activeThe transaction and owner are still live.Continue or finish that transaction; do not start another.
active_unknown_owner, unverified_listener, owned_runtime_without_lease, or replacement_runtimeOwnership or runtime identity is not safe to infer.Fail closed. Do not terminate or adopt the runtime.

A missing receipt does not prove that a lease is stale. A port that answers does not prove that it belongs to this transaction. The absence of identity is itself a blocker.

08 / mechanics

A minimal standalone runbook

The following is the mechanical shape; authorization and lane choice still come from the workflow above. Replace the synthetic target with the exact approved target. Use a real Auth Vault profile only when it has been identified outside the report.

SKILL_DIR=/path/to/webflow-designer-agent-browser
CLI="$SKILL_DIR/bin/webflow-browser"
TARGET='https://design.webflow.com/?pageId=synthetic-page'

printf '%s\n' '{"version":1,"operation":"status"}' \
  | "$CLI" status

cat <<JSON | "$CLI" prepare
{
  "version": 1,
  "operation": "prepare",
  "transport": "native",
  "mode": "isolated",
  "target": "$TARGET",
  "surface": "body",
  "readySelector": "body"
}
JSON

# Execute the returned actions exactly. Then classify compact evidence:
cat <<'JSON' | "$CLI" verify
{
  "version": 1,
  "operation": "verify",
  "transactionId": "<transaction-id-from-prepare>",
  "transport": "native",
  "surface": {
    "url": "https://design.webflow.com/?pageId=synthetic-page",
    "title": "Webflow - Example site",
    "document": "designer",
    "authenticated": true,
    "errorPage": false,
    "scope": "body",
    "scopeObserved": true
  }
}
JSON

Proceed only when verify reports a ready Designer surface and permits the requested work. Always finish:

cat <<'JSON' | "$CLI" finish
{
  "version": 1,
  "operation": "finish",
  "transactionId": "<transaction-id-from-prepare>",
  "transport": "native"
}
JSON

Inspect the finish JSON for the five stopped-runtime fields before running the returned retireAfterFinish action. Native requests omit session; CLI requests require a named session and use it consistently through close.

09 / record

Record enough to make the result useful

A recorded result should include the exact sanitized URL, ownership boundary, mode, transport, target frame, readiness checks, before and after semantic observations, authorized actions, relevant diagnostics, blockers, assumptions, and stopped-runtime proof.

Use the mode-specific report template from scripts/automation-evidence.py and validate the sanitized report. Keep temporary reports outside the repository and remove them after review. A report that omits cleanup is incomplete even when its assertion passed.

Current boundary. The managed Designer profile available is currently unauthenticated, so live Designer inspection is blocked at the authentication gate. No live customer surface or private browser evidence is represented in these pages.

Figures use the self-contained Webflow wf-viz kit: the repository’s template, tokens, timeline runtime, and hostile-host verification. The pages make no network request to render.
