Webflow browser / why the workflow is shaped this way

A Designer run is a contract, not a script.

When you ask a browser to inspect or change a Designer document, two questions have to stay distinct: what is this run allowed to do, and what does the browser prove before it does it? The workflow answers both questions without making the Webflow user learn every browser detail.

The contract also catches the cases where the browser reaches the wrong document. It covers the rest of the run too: ownership, readiness, evidence, privacy, and cleanup.

01 / purpose

What this workflow is protecting

A Designer browser task is not complete because a process started, a command returned, or a selector existed. It is complete when the intended work is authorized, the browser is the right browser, the observed surface is the right surface, and the runtime is left in a known state.

Each name points to a different failure, safe stop, or piece of proof a maintainer can review later. That is more useful than treating every surprise as browser flakiness.

  • Judgment. A Webflow user decides whether the task is observation or change, whether a live state must be preserved, and what authorization the action needs.
  • Proof. The workflow checks target identity, runtime ownership, service readiness, surface identity, evidence scope, and cleanup.
  • Handoff. The browser caller receives a bounded plan and executes it in order. It does not improvise a second browser or silently skip a check.
Core idea. A reusable workflow should make the safe path easy to repeat and the unsafe path easy to name. It should not make a decision on the user’s behalf merely because a command is available.
02 / terms

Four terms make the rest easier to read

  • Target. The exact Webflow URL and document the task names. Preserve meaningful query values such as pageId and simulateRole.
  • Surface. What the browser actually shows: its URL and title, document type, authentication state, and the frame or feature area being inspected.
  • Runtime and lease. The managed Chrome for Testing process and the exclusive record that says which transaction owns it.
  • Transport. The way the caller controls the browser. The workflow supports native agent_browser or the explicit CLI fallback, but the choice stays fixed for the run.
03 / shape

The useful boundary is between judgment and proof

The workflow has a judgment side and a repeatable side. The judgment side supplies intent and authorization. The repeatable side checks the declared conditions, keeps one owner on the managed runtime, and returns a result that can be inspected without exposing browser state.

Pi, a shell, and CI can carry the request. The lifecycle should answer the same safety question consistently for each one.

One safe Designer run has two responsibilities

Judgment sets the boundary; the lifecycle proves the handoff.

The boundary does not remove judgment. It keeps judgment where a Webflow user can see it, while the proof rules remain the same for every caller.

The lane follows the effect, not the transport

Read-only observation is fast; stateful or uncertain work is guarded.

Attached versus isolated chooses where state comes from; fast versus guarded chooses what the work may change. They are separate decisions.

04 / reasons

What each responsibility protects

Each responsibility has a concrete job: it names a failure, stops unsafe work, or leaves proof a maintainer can review.

ResponsibilityWhat it coversWhy it exists
Task judgment Intent, authorization, attached versus isolated mode, and the fast or guarded lane. A tool cannot infer whether a visible state may be changed or whether another person is relying on it.
Target and surface The exact URL, title, document type, approved origin, and selected frame or feature surface. A successful navigation can still land on login, an error document, an empty shell, or the wrong iframe.
Runtime ownership Managed Chrome for Testing identity, generation, process, and exclusive lease. The transaction must never reuse or close another task’s browser, even when a port happens to answer.
Readiness The HUD, Designer service, exact target HTTP response, browser profile, and Designer surface. Named checks turn an environment gap into a blocker instead of letting a later page failure look like product behavior.
Evidence and privacy Compact semantic observations, scoped screenshots, and filtered diagnostics. Review needs enough proof to decide; it does not need cookies, storage, tokens, raw DOM, or a full Designer model.
Cleanup Lease release, runtime stop, no consumer, and a public stopped receipt. A test that leaves a browser behind has not finished, even if its page assertion passed.
05 / paths

Two ways to carry the same promise

Pi is the natural home for judgment: the skill asks for the exact target, decides whether an action is fast or guarded, and coordinates the browser interaction. A non-Pi caller may need the same lifecycle from a shell or CI. It should not get a weaker version of ownership or cleanup just because its entrypoint is different.

The standalone command carries the same workflow to another host. It accepts a small request, returns a bounded plan or classification, and leaves page interaction to the selected browser transport. The Pi adapter uses the same lifecycle rules.

For maintainers, this boundary has a few useful names. The lifecycle is the core module; the JSON commands are its small interface; and the Pi compatibility layer is a thin adapter at the seam. That depth gives both callers leverage from one ownership or cleanup fix, while locality keeps task judgment close to the Webflow user.

Pi path

The skill owns authorization, judgment, lane selection, and orchestration. Its compatibility adapter uses the shared lifecycle and returns the same kinds of readiness and cleanup decisions.

Standalone path

bin/webflow-browser serves shell automation, CI, and other hosts. Its JSON protocol makes the handoff inspectable without putting credentials or raw browser state on stdout.

06 / effect

Choose the lane by what the work can change

Attached versus isolated answers where the state comes from. Fast versus guarded answers what the action may affect. They are separate decisions, and neither transport choice settles them.

LaneUse it forExtra proof
Fast Read-only observation after target, ownership, and all five readiness checks are verified. Keep snapshots and diagnostics scoped. Do not navigate, select, edit, publish, or trigger an app action.
Guarded Navigation, reload, selection changes, canvas edits, undo, redo, publish, connected-app actions, or uncertain effects. Capture a small baseline, obtain authorization, perform one bounded action, then verify its postcondition and unrelated state.

A fast lane is not a shortcut around the lifecycle. It still needs the exact target, the ownership boundary, privacy limits, readiness, and stopped-runtime proof. An unclassified action is guarded or blocked.

07 / how

The CLI is small on purpose

The mechanics fit in a short section. The CLI does not replace the workflow judgment above; it makes the repeatable parts available to another host. Each command reads at most one versioned JSON request and writes one sanitized JSON result.

CommandWhat it doesWhat it does not do
prepareValidates the declaration, runs service preflight, starts and claims the managed runtime, and returns ordered browser actions.It does not open the page or take a snapshot.
verifyRechecks services and runtime identity, then classifies compact surface evidence. It does not authorize a mutation.
statusClassifies the current transaction, runtime, and lease without changing them.It does not infer that an unknown owner is safe.
reconcileRecovers only a stale state that status marks safe.It does not take ownership of an active or unknown runtime.
finishReleases the exact transaction and proves the runtime stopped.It does not sign out, clear cookies, or reset authentication.
cleanupAlias for finish.It does not change the cleanup order.

One request in, one bounded result out

A native request names the target, mode, transport, surface, and readiness selector. It omits the CLI-only session field. A CLI transport request requires a task-owned named session. An authProfile is allowed only for an explicitly identified dedicated Webflow profile in isolated mode; it is not a credential.

CLI="$SKILL_DIR/bin/webflow-browser"
printf '%s\n' '{"version":1,"operation":"status"}' \
  | "$CLI" status

cat <<'JSON' | "$CLI" prepare
{
  "version": 1,
  "operation": "prepare",
  "transport": "native",
  "mode": "isolated",
  "target": "https://design.webflow.com/?pageId=synthetic-page",
  "surface": "body",
  "readySelector": "body"
}
JSON

The prepare result contains a transaction ID and an ordered handoff: connect, optional Auth Vault login, exact-target open, and wait. The caller executes those actions without substitutions, then sends compact evidence to verify. The result never contains credentials, cookies, raw DOM, customer data, or full browser state.

Read the result, not just the exit code

Exit codes are a stable shell summary. The JSON classification explains what happened and what a human should do next.

CodeMeaningTypical response
0Command completedInspect the JSON; a prepared transaction still requires verify and finish.
1Lifecycle or cleanup failure Stop and inspect the named failure; cleanup is not inferred.
2Invalid command or requestFix the protocol input before trying again.
3Readiness or authentication blocker Resolve the named blocker or stop.
4Ownership or transaction conflict Do not reuse a runtime; inspect status and reconcile only when it says recovery is safe.

A successful status: "reconciled" means the classified stale state was safely converged. A successful prepare means the handoff is ready, not that QA may begin; verify must still report a verified Designer surface.

08 / practice

Use this checklist before calling a run reliable

  1. Is the exact target supplied, including the meaningful query parameters, host, and port?
  2. Is the selected mode attached or isolated, and is the chosen transport available for the entire run?
  3. Is the work read-only, or has guarded authorization and a mutation baseline been obtained?
  4. Did the workflow name the five readiness checks instead of relying on one familiar Designer control?
  5. Will evidence be compact, scoped, temporary, and free of credentials, cookies, tokens, raw DOM, and customer data?
  6. Will the caller finish the transaction, inspect the stopped proof, and only then close its automation session?
Current boundary. The managed Designer profile available is currently unauthenticated, so live Designer inspection is blocked at the authentication gate. The guides and figures were checked offline; they are not a substitute for a live authenticated surface.
